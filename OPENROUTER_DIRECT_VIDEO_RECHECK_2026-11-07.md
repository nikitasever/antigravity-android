# OpenRouter video API непосредственно на телефоне, 2026-11-07

Продолжение OPENROUTER_VIDEO_CONTROLS_RECHECK_2026-11-07.md.

## Контракт

При выборе ресурсов телефона и непустом ключе OpenRouter видеогенерация идёт
непосредственно в официальный API, без разрешения адреса PC-Bridge. Для режима
ПК и прежнего сценария с ключом, настроенным только на мосту, сохраняется старый
маршрут. После создания задачи её транспорт не меняется при переключении
текущего чата, ключа или URL моста. Автоматического fallback после запуска нет.

DirectOpenRouterVideoClient использует GET /videos/models, один POST /videos,
GET /videos/{id} и /content?index=0. Выбранный ID проверяется в dedicated каталоге;
другая модель не подставляется. Если заявлены длительности, выбирается минимальная
положительная целая. Остальные параметры остаются штатными для выбранной модели;
это не утверждение о минимальной цене или поддержке всех опций/референсов.

Официальные источники, проверенные в этом проходе:
- https://openrouter.ai/docs/guides/overview/multimodal/video-generation
- https://openrouter.ai/docs/api/api-reference/video-generation/create-videos

## Долговечность и отмена ожидания

Журнал v2 читает старые bridge-записи v1. Новые поля transport,
submissionAttempted и providerJobId не содержат ключ или подписанный URL.
Транспорт/исходный ключ/модель/чат не переназначаются; providerJobId после первой
записи неизменен, submissionAttempted не сбрасывается.

До POST долговечно записывается submissionAttempted. После ответа ID сохраняется
перед опросом; запись ID защищена от отмены корутины. Из известного ID восстановление
запрашивает только статус/файл. Если POST мог быть отправлен, а ID неизвестен,
повторная генерация блокируется, включая новый процесс. Если POST доказуемо ещё
не предпринимался (подготовка/каталог), может быть выполнен первый запуск исходного
сохранённого намерения. Это не распределённая exactly-once гарантия.

Штатные Stop/Resume и исходный чат используются и для прямого API. Временный чат
держит состояние в памяти, без постоянного журнала. Остановка наблюдения не
означает отмену или прекращение тарификации у провайдера.

## Файл и ключ

Контент скачивается в app-private каталог generated_media на телефоне через
.part, fsync и замену после проверки размера и MP4/WebM-заголовка. Лимит — 256 МБ,
не более трёх перенаправлений HTTPS. Ключ посылается только в первоначальный
канонический content-запрос, не на CDN. polling_url и подписанные URL провайдера
не используются как произвольные авторизованные адреса и не сохраняются.

Вложение содержит путь на телефоне и пустой mediaUrl: авторизованный endpoint
не выдаётся за публичную ссылку. Карточка использует FileProvider; проигрывание
зависит от реального файла и установленного просмотрщика. Удалённый локальный
файл не называется доступным по ссылке. Результат и журнал ожидания удаляются
в правильном порядке: сначала файл и исходная история, потом checkpoint.

Для контента принимается только HTTP 200. Тест с 206 и Content-Range сначала
воспроизвёл ошибочное принятие частичного MP4; лог сохранён в
uploads/direct-video-partial-response-red.log. После исправления тот же сценарий
должен отвергать частичный ответ и оставлять ранее сохранённый файл. ID провайдера
`.`/`..` отвергаются в Android и Node, чтобы не нормализовать путь API к родителю.

Сохранение ключа и выбор OpenRouter-модели в режиме телефона больше не копируют
ключ в конфиг ПК. При разрешённой синхронизации в режиме ПК адрес и ключ берутся
из контекста самого действия, а не из настроек после асинхронного переключения.
Существующая независимая синхронизация избранного/рабочих областей с ПК не
отключалась по признаку режима выполнения. Это отдельный metadata POST, не
видеозапуск и не передача API-ключа. В нативном тесте мост возвращает для записи
503; успех прямого видео не должен зависеть от этой синхронизации.
