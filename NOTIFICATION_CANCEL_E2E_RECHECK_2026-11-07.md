# От уведомления до отмены задачи ПК — 7 ноября 2026

## Сценарий

SubagentCancellationIntegrationTest создаёт настоящий Android ViewModel через
ViewModelProvider. Адрес локального тестового моста A выставляется заранее через
обычный экран настроек. Private prefs и история напрямую не подменяются.

Два HTTP-моста A/B поднимаются на ПК с настоящим pc-bridge/lib/subagent-runtime.js.
Подменён только run: контролируемый исполнитель ждёт AbortSignal, не запускает
CLI, модель или команды проекта. Состояние содержит счётчики фактических start,
abort, cancel requestId, статусы и ID. Содержимое пользовательских файлов и
полные промпты не записываются.

1. ViewModel запускает A; тест сохраняет настоящую кнопку её уведомления.
2. Новый чат инициирует отмену A. Её ответ намеренно задержан на 1,5 секунды.
   Android переключается на мост B и запускает новую пачку.
3. Поздний ответ A не должен заменить строки B. Старая кнопка A не должна вызвать
   cancel на B или скрыть её новое уведомление.
4. Настройки возвращаются на адрес A. Кнопка уведомления B должна всё равно
   отправить отмену на исходный B с его requestId.
5. Проверяются реальный abort обоих работников B, освобождение слотов runtime,
   терминальные статусы ViewModel и правильные cancel ID на обоих мостах.

## Границы

Это не запуск коммерческой модели или CLI: HTTP, Android ViewModel, системный
PendingIntent/receiver и SubagentRuntime настоящие, исполнитель контролируемый.
Автоматически исполняется PendingIntent.send, а не жест в системной шторке.
Проверка выполняется на принадлежащем задаче эмуляторе, не на телефоне пользователя.
Старт ViewModel также выполняет обычную инициализацию приложения на тестовом AVD.

Первый запуск сборки теста остановился на неподдерживаемой Kotlin-ссылке на
локальный lateinit. Исправлена только проверка инициализации тестового объекта;
лог сохранён в uploads/notification-cancel-build.log.

HTTP-обвязка стенда воспроизводит маршрут `/api/agents/swarm`, но полный
`server.js`, его авторизация и запуск реальных дочерних процессов здесь не
исполняются. Отмена проверяется после принятия dispatch; гонка отмены до его
принятия и восстановление после смерти Android-процесса остаются отдельными
сценариями.

## Повторение

Сохранён `pc-bridge/test/fixtures/notification-cancel-bridge.cjs`. Единственное
отличие от использованного файла в uploads — относительный путь require после
перемещения. Выполнены `node --check` и проверка запуска обоих HTTP-слушателей.
Запускать из корня проекта, с существующей папкой uploads и свободными портами:

```powershell
node pc-bridge/test/fixtures/notification-cancel-bridge.cjs
```

Использовать только отдельный QA-эмулятор: установить debug и androidTest APK,
разрешить уведомления, выставить через обычные настройки
`http://127.0.0.1:8810` и выключить ограничение на публичный HTTPS. Сначала
сохранить прежние значения для последующего восстановления. Пробросить порты:

```powershell
adb -s emulator-5560 reverse tcp:8810 tcp:8810
adb -s emulator-5560 reverse tcp:8811 tcp:8811
adb -s emulator-5560 shell am instrument -w -r -e class 'com.google.antigravity.SubagentCancellationIntegrationTest#notificationCancellationUsesOwnerBridgeAndCannotCancelANewerBatch' com.google.antigravity.test/androidx.test.runner.AndroidJUnitRunner
```

Перед каждым повтором запускать свежий процесс стенда: счётчики предназначены
для одного сценария. Выбирать конкретный метод, а не весь класс: второй сценарий
в классе требует отдельного запуска стенда с --hold-dispatch-a.
По завершении восстановить настройки/разрешение, остановить
стенд и QA-эмулятор. Не запускать сценарий на личном телефоне: он создаёт QA-чаты.
