# План переноса навыков, плагинов и MCP из Claude и ChatGPT

Дата исследования: 2 ноября 2026. Статус: план; Этап 0 выполнен и проверен,
Этап 1 выполнен 2 ноября 2026 (инвентарь без установки расширений), Этап 2
выполнен 2 ноября 2026 (парсеры форматов и общий реестр, без установки
расширений источников), Этап 3 выполнен 2 ноября 2026 (реальные MCP-клиенты:
транспорты, рукопожатие, вызовы инструментов и проброс авторизации без утечек;
полный OAuth-цикл — за границей шага).

## Цель и границы

Добавить в Antigravity весь выявленный набор расширений из доступных референсов
Claude и ChatGPT: навыки, пакеты плагинов, подключения к сервисам и MCP-серверы.
Обеспечить реальное выполнение в разговорах и дочерних задачах, на телефоне и
через ПК. У каждой позиции должны быть источник, способ адаптации, зависимости,
место исполнения, проверка и явный статус. Приоритеты ниже определяют очередность,
а не сокращают общий объём до нескольких популярных расширений.

Каталоги меняются: сначала фиксируем полный доступный срез с датой, версией,
страницами/категориями и границами доступности. Затем обновляем его по разнице.
Нельзя заранее назвать конечное количество или обещать перенос закрытого
серверного компонента, которого нет в APK, открытом исходнике или доступном API.
Такие позиции остаются в общей матрице с конкретной зависимостью; их нельзя
незаметно исключить или объявить работающими по наличию карточки.

Проверенные дефекты, которые нужно устранить до массового импорта:

1. `seedDefaultPluginsIfEmpty` создаёт пакеты по описанию; `managePlugin` для
   неизвестного имени также собирает один manifest. Наличие такого manifest не
   подтверждает обещанную функциональность.
2. `listSkills` может копировать отключённый autonomous-software-engineer обратно
   в активный файл. Просмотр не должен отменять отключение пользователя.
3. `listMcpServers` присваивает connected по enabled, а имена инструментов для
   части серверов задаёт вручную. Настроен, включён и действительно подключён —
   разные состояния.
4. Android-модели расширений преимущественно описывают ПК; в них недостаточно
   данных о совместимости, правах, полном составе, проверке и месте исполнения.

Точки входа: `AntigravityBackendClient.kt`, `PhoneAgentEngine.kt`,
`AntigravityModels.kt`, `Round5PanelsAndSheets.kt`, `AntigravityViewModel.kt`,
`pc-bridge/server.js`, `pc-bridge/mcp_sysinfo_server.js`.

## 2. Что именно переносим

| Тип | Содержимое | Способ адаптации |
|---|---|---|
| Навык | SKILL.md, метаданные, references, assets, scripts | Импорт всего пакета; проверка ссылок и зависимостей; загрузка инструкций по необходимости |
| Плагин | Manifest и набор навыков, инструментов, агентов, hooks, других компонентов | Разбор каждого компонента, сохранение версии и происхождения; отчёт совместимости перед установкой |
| Connector / App | Подключение сервиса, аутентификация, инструменты, иногда интерфейс | Публичный MCP endpoint либо официальный API; собственная авторизация Antigravity |
| MCP-сервер | Исполняемый сервер или удалённый endpoint, tools/resources/prompts | Настоящий MCP-клиент и подходящий исполнитель, проверка протокола и авторизации |
| Закрытая встроенная функция | Серверный инструмент продукта без переносимого исходника | Отдельная реализация через доступный API/компонент; честная зависимость в матрице |

Claude.ai, Claude Code, Cowork, ChatGPT и Codex отмечаются как разные источники.
Плагин Codex нельзя автоматически считать плагином Android ChatGPT. Совпадение
названий и строк APK не доказывает переносимость или одинаковый доступ аккаунта.

## 3. Целевая архитектура

Общая цепочка: каталог → проверка пакета → реестр установленного → выбор навыка /
инструмента → проверка разрешений → исполнитель → результат в разговоре.

- `ExtensionRegistry`: идентичность, издатель, исходный тип/продукт, версия,
  источник, лицензия/доступ к распространению, хэш, состав, зависимости,
  совместимость и проверенные возможности.
- `SkillResolver`: метаданные в доступном каталоге, содержимое выбранного навыка
  по запросу; корректные относительные пути к ресурсам и скриптам.
- `ToolRegistry` и `ToolRouter`: единый контракт name/schema/result/cancel/error,
  раздельные пространства имён пакетов и выбор исполнителя.
- `Policy`: доступные действия и ресурсы для конкретного разговора/дочерней
  задачи. Разрешение установки не расширяет автоматически доступ инструментов.
- `Executors`: Android, PC-Bridge, удалённый MCP. Место модельного инференса
  задаётся отдельно от места выполнения инструмента.
- `ConnectionStore`: аккаунт, область доступа, срок и отзыв подключения;
  секреты — отдельно от переносимого каталога и обычных резервных копий.

Предлагаемые состояния: найдено → проверено → установлено → требует входа /
зависимостей → доступно в текущем режиме. Сетевое соединение имеет собственные
состояния connecting / ready / expired / offline / error. «Установлено» не
приравнивается к «может выполнить задачу».

## 4. Телефон, ПК и облако

| Сценарий | Телефон | ПК / внешний сервис |
|---|---|---|
| Инструкционный навык | Хранение и загрузка в контекст | Не нужен, если зависимости отсутствуют |
| Поиск/запись файлов Android | PhoneResourceController по разрешениям | Не переносить в файловую систему ПК |
| Удалённый MCP | MCP-клиент Android, HTTPS, собственный вход | Сервер поставщика |
| Локальный stdio MCP | Только после проверки Android-совместимого runtime | Сначала поддержка через PC-Bridge; Node/Python-сервер не объявляется Android-совместимым автоматически |
| Скрипты навыка | Проверенный Android-исполнитель и поддерживаемые зависимости | Иначе ПК; карточка явно показывает эту зависимость |
| Gemini CLI + инструменты телефона | Оркестрация и Android-инструменты | Выбранная модель через мост; её источник не меняет цель инструмента |
| Дочерняя задача | Тот же реестр, явно ограниченный контекст и права | Не наследует произвольные права родителя или все подключения |

Android-поддержка локальных runtimes — отдельная обязательная ветвь плана для
позиций, которым она нужна. Нельзя заменить требование работы на телефоне
постоянным скрытым перенаправлением всего на ПК.

## 5. Этапы и критерии готовности

### Этап 0 — исправить достоверность текущего менеджера

Убрать создание фиктивной функциональности по manifest, автоактивацию при чтении,
ложный connected; сохранить настройки отключения. Отделить редактор нового
пакета от установки готового. Ошибки CLI/HTTP не превращать в успешную операцию.

**Готово:** пустой каталог остаётся пустым; просмотр ничего не устанавливает;
отключённое остаётся отключённым; статус готовности требует проверки.

**Статус: выполнено 2 ноября 2026 (раунд 22).** Конкретные изменения:
- `seedDefaultPluginsIfEmpty` удалён — автозасев «antigravity-workspace-guard»
  и «kotlin-compose-inspector» по описанию больше не создаётся на старте.
- `managePlugin`: `install` принимает только реальный путь/URL (иначе честная

**Готово:** импорт → просмотр → установка → перезапуск → отключение → удаление

старым HTTP+SSE включать по потребностям реестра. Реализовать initialize,
согласование версии, tools/list, tools/call, resources/prompts при объявленной
поддержке, pagination/list_changed, JSON/schema ошибки, тайм-аут, отмену,
переподключение и жизненный цикл. Не собирать список tools по имени сервера.

Авторизация удалённых сервисов — по актуальной спецификации MCP и требованиям
провайдера: discovery, OAuth, PKCE для мобильного клиента, refresh/revoke,
изолированное хранение токенов и отсутствие секретов в журналах.

**Готово:** соединение и один реальный вызов на каждом поддерживаемом транспорте;
проверены истёкший вход, отключённый сервер, Stop, отказ инструмента и reconnect.

**Статус: выполнено 2 ноября 2026 (ядро транспортов и жизненного цикла).**

- Модуль `pc-bridge/lib/mcp-client.js`: настоящие транспорты stdio (дочерний
  процесс), Streamable HTTP (POST, Mcp-Session-Id, ответы JSON или SSE) и
  устаревший HTTP+SSE (событие endpoint + POST сообщений); жизненный цикл
  initialize → notifications/initialized → tools/list. Статус «connected»
  выставляется ТОЛЬКО после полного успешного рукопожатия — если tools/list не
  ответил, соединение не подтверждается. Список инструментов — только из живого
  tools/list (с постраничным обходом nextCursor), resources/prompts — при
  объявленной сервером поддержке; обрабатываются notifications/tools/list_changed,
  ошибки JSON-RPC и схемы ответа (protocol_error/tool_error), согласование версий
  (незнакомая версия сервера — честный version_unsupported), тайм-ауты
  (handshake_timeout/request_timeout), отмена (Stop: AbortSignal +
  notifications/cancelled), reconnect и авто-переподключение перед вызовом без
  автоматического повтора самого вызова (без двойного побочного эффекта).
- Авторизация: env/headers/Bearer-токен пробрасываются из конфига в транспорт;
  значения вырезаются из всех текстов ошибок, результатов tools/call и описаний
  (redactSecrets), в логи и публичные ответы API попадают только имена ключей
  (describeDescriptor). Истёкший вход (HTTP 401/403) — auth_failed без утечки
  значения токена (проверено эхом токена от сервера).
- Подключение: `POST /api/mcp` в `pc-bridge/server.js` (действия probe/check,
  call, disconnect) поверх `McpClientManager`; `GET /api/mcp` отдаёт live-статус
  и tools только после проверки, без проверки — честно «настроен» с пустым
  списком (старое «честное исключение» со статическими именами удалено).
  Android: `AntigravityBackendClient.probeMcpServer/callMcpTool`,
  `AntigravityViewModel.checkMcpServer/callMcpTool`, карточка MCP в MainScreen с
  честными статусами (`describeMcpStatus`), живым списком инструментов, кнопкой
  «Проверить» и диалогом реального вызова инструмента; ложное «connected» при
  включении сервера убрано (оптимистичный статус — «настроен»).
- Проверено: 20 интеграционных тестов `pc-bridge/test/mcp-client.test.js`
  (реальные рукопожатия на всех трёх транспортах, включая настоящий
  `mcp_sysinfo_server.js`; отказ соединения, таймауты рукопожатия и вызова,
  падение процесса до и после подключения, 401, Stop, reconnect, пагинация,
  version_unsupported, protocol_error, редактирование секретов) и
  `extensions-stage0.test.js` (connected только после рукопожатия); вся
  коллекция Node-тестов (89) зелёная. Smoke на реальной конфигурации: оба
  сервера (`ag-workstation-info` и `rea`) подключены настоящим рукопожатием,
  инструменты получены живым tools/list (у `rea` — 200 имён), реальный
  tools/call выполнен на обоих. Android: testDebugUnitTest lintDebug
  assembleDebug — BUILD SUCCESSFUL, 84 юнит-теста (21 набор) без падений, включая
  новый `McpLiveStatusTest` (честность статусов connected/configured/failed).
- Границы: полный цикл OAuth по спецификации MCP (discovery, PKCE для
  мобильного клиента, refresh/revoke, изолированное хранение токенов) не
  реализован — в этом шаге проброс параметров авторизации и отсутствие утечек;
  серверы, требующие OAuth-входа, честно вернут auth_failed до реализации
  входа. Транспорт живёт в pc-bridge; Android управляет соединением через мост
  (probe/call), прямой Streamable HTTP из приложения не требуется.

### Этап 4 — подключить реестр к моделям и дочерним задачам

Загрузить метаданные доступных навыков, затем только выбранные инструкции и
необходимые ресурсы. Передавать реальные схемы разрешённых инструментов в
Gemini/OpenRouter/CLI-адаптеры, результаты возвращать в тот же цикл. Проверять,
как CLI предоставляет инструменты: не предполагать произвольную инъекцию схем
без подтверждённого механизма. Сохранить работу существующих phone_action.

Не делать одноимённые инструменты разных серверов взаимозаменяемыми; не
перенаправлять запрос телефона на ПК из-за отсутствующего Android-runtime.
Дочерним задачам выдавать только нужный поднабор прав; annotations MCP сами по
себе не доказывают, что инструмент безопасен или только читает.

**Готово:** навык реально выбирается, инструмент выполняется на указанной стороне,
ответ опирается на результат; Stop отменяет вызов; запрет доступа действует.

### Этап 5 — адаптеры компонентов плагинов и Android-runtime

Для всех components из инвентаря определить сохранение исходника, преобразование
или собственный исполнитель. Отдельно проверить commands, agents, hooks, LSP,
локальные программы, переменные конфигурации и продуктовые UI-компоненты.
Недопустимые/неподдерживаемые hooks не запускать молча. Для скриптов подготовить
зависимости и изоляцию рабочего каталога; Android-совместимость доказывать запуском.

**Готово:** у каждого компонента есть проверенный путь исполнения либо конкретный
блокер. Статус «плагин поддержан полностью» разрешён только после проверки всего
нужного ему состава. Проверять право переиспользования/распространения оригинала.

### Этап 6 — единый интерфейс расширений

Вход «Расширения»: Подключения / Навыки / Плагины; внутри Мои / Каталог, поиск,
категории, источник и совместимость. Технические MCP-параметры — в подробностях
подключения. Карточка показывает состав, доступные инструменты, права,
исполнитель, зависимости, источник оплаты/лимитов если они проверены, и
последнюю успешную проверку. Действия: установить, войти, включить, проверить,
обновить, отключить, удалить. Не показывать неподключённый сервис рабочим.

В разговоре — выбор подключения/навыка и настоящие события инструментов.
Сохранять существующую хронологию, результаты, ошибки и Stop; отдельная панель
ручного создания субагентов этим не добавляется.

**Готово:** установка/вход/отключение понятны на телефоне, статусы не противоречат
реальному исполнению; проверены Back, клавиатура, длинные имена и крупный шрифт.

### Этап 7 — перенос всех позиций по матрице

Сначала сквозные контрольные пакеты: один инструкционный навык; один навык со
скриптом; один HTTP MCP; один stdio MCP; один составной плагин с зависимостями.
Это проверка инфраструктуры, а не конечный набор.

Далее проходить весь инвентарь пакетами: документы и PDF; таблицы/презентации;
код и Git; поиск/браузер; дизайн/медиа; почта/календарь/диск; задачи/знания;
остальные категории зафиксированных каталогов. Названия внешних сервисов не
гарантируют наличие переносимого сервера: путь подтверждать для каждой позиции.

**Готово:** каждая позиция полного среза имеет адаптацию и сценарий проверки;
нерешённые зависимости остаются в общем backlog, с владельцем и следующим шагом.
Общий перенос нельзя объявить завершённым, пока обязательные позиции заблокированы.

### Этап 8 — сохранение, обновления и восстановление

Локально хранить каталог, версии, права, привязки разговоров, результаты и
технический статус. Хранение секретов отделить от общей синхронизации. Резервная
копия по умолчанию содержит manifests/настройки без токенов; восстановление явно
показывает необходимость повторного входа. Обновление пакетов с возможностью
отката, сравнение новых прав и зависимостей, сохранение отключений.

**Готово:** перезапуск/обновление/восстановление не запускают платные вызовы,
не теряют отключённые пакеты и не расширяют права без предусмотренного действия.

## 6. Экономичное исполнение

Не включать весь каталог в каждый промпт. Сначала метаданные и релевантные
возможности; полные инструкции, схемы и файлы — по необходимости. Кэшировать
каталоги, manifests и схемы с инвалидацией по версии/list_changed. Ограничивать
размер результатов и число шагов; показывать фактические вызовы. Подзадачам
передавать минимум достаточного контекста и проверять результаты. Не менять
выбранную модель скрытно ради экономии. Новые инструменты доступны существующим
моделям через проверенные адаптеры; список установленных пакетов сам по себе
не должен создавать платные модельные вызовы.

## 7. Общая приёмка

- 100% учёт зафиксированного среза, отчёт о покрытии и отсутствие выдуманных карточек.
- Сквозной сценарий для каждого перенесённого расширения, а не только тест парсера.
- Матрица: телефон+API, телефон+CLI-инференс, ПК+CLI, отключённый ПК,
  нет сети, истёкший OAuth, недостаточные права, длинный ответ, Stop и перезапуск.
- Установленный, включённый, подключённый и проверенный статусы различаются.
- Текст файла/описание плагина не может самостоятельно выдавать новые разрешения.
- Пользовательские отключения сохраняются; обновление не устанавливает пакеты
  автоматически из одного имени; секреты не попадают в Git/APK/экспорт.
- Android unit tests, Node tests, lint, assemble и визуальные проверки новых
  экранов. Отдельно реальные вызовы MCP и тесты каждой поддерживаемой авторизации.
- Проверка физического телефона: ресурсы Android исполняются именно там, а
  необходимость ПК или внешнего сервиса явно отражается до запуска.

Порядок старта: исправления менеджера → инвентарь/матрица → реестр/импорт →
MCP/авторизация → модельный цикл → адаптеры и UI → весь каталог → обновления и
полная приёмка. Детальные сроки оценивать после инвентаризации и контрольных
пакетов; до этого точная оценка «всех расширений» не обоснована.
