# Видеозадачи OpenRouter через PC-Bridge — 7 ноября 2026

Продолжение: OPENROUTER_VIDEO_RECOVERY_RECHECK_2026-11-07.md описывает добавленный
журнал Android, восстановление в исходный чат и проверки файлов/временного чата.
Ниже сохранены результаты предыдущего прохода; его список ограничений относится
к состоянию до этих изменений.

## Реализовано

На мосту вместо постоянного 501 работают три POST-маршрута:

| Маршрут | Назначение |
|---|---|
| /api/openrouter/generate-video | Один запуск с requestId, model, prompt и необязательными duration/resolution/aspect_ratio |
| /api/openrouter/video-status | Опрос уже созданной задачи по requestId |
| /api/openrouter/video-download | Получение готового файла в generated_media и возврат обычного media attachment |

`OpenRouterVideoJobs` использует официальный POST /api/v1/videos, затем GET по
сохранённому ID и авторизованный content endpoint. Параметры проверяются по
dedicated видео-каталогу. Без явно заданной длительности выбирается минимальная
положительная поддерживаемая длительность, а не выдуманные общие 3 секунды.
Модель не подменяется. Этот маршрут пока text-to-video: референсы, callback_url
и provider options явно отвергаются, а не молча игнорируются.

API запуска возвращает 202/job. Android теперь понимает этот ответ: один submit,
до 40 status-запросов с паузой 30 секунд, затем video-download. Он больше не
принимает 202 за готовый видеофайл с адресом корня моста. При сетевом сбое или
исчерпании ожидания новый submit автоматически не выполняется. Пауза не означает
отмену задачи у провайдера. В клиенте есть отдельный resume-режим status-only;
его подключение к восстановлению ViewModel пока осталось отдельной задачей.

Адрес моста, ключ, ID и модель фиксируются в начале. Редиректы и транспортный
повтор отключены. UUID сообщения используется как requestId. Повторные нажатия
во время текущей генерации не создают ещё одну задачу. Новый чат получает ID до
сохранения медиасообщений. Прогресс и результат пишутся в исходную переписку,
включая случай перехода в другой чат; настройки в середине цикла не меняют маршрут.

После получения файла Android использует штатное сохранение на телефон. Если
запись не удалась, сообщение говорит об этом, сохраняя ссылку на файл моста.
В тексте результата не придумываются неизвестные длительность, разрешение или
кодек. Существующая карточка медиа ещё требует отдельной UI-правки (см. ниже).

## Журнал и защита от повторной платной отправки

`pc-bridge/openrouter-video-jobs.json` локальный и исключён из git. Он записывается
атомарно с fsync до платного POST и после получения provider job ID. Сохраняются
requestId, модель, хеш нормализованного запроса, SHA-256 исходного ключа, статус,
provider job ID, время и локальная метаинформация файла. Сам ключ, промпт и
подписанные ссылки не сохраняются. Хеш ключа не возвращается в публичном job.
Ограничение — 1000 записей; при заполнении новая платная отправка не выполняется.
Автоматического удаления неопределённых записей нет.

- Совпадающие ID/содержимое/ключ делят один запуск; после перезапуска возвращается
  уже известная задача. Другой промпт с тем же ID получает 409, другой ключ — 403.
- При утрате ответа POST статус становится unknown. После смерти процесса в
  submitting он также восстанавливается как unknown. Нового платного POST нет.
- Это не распределённая exactly-once гарантия: если OpenRouter принял POST, а
  ответ потерян до сохранения ID, автоматического способа найти этот ID здесь нет.
  Не выдумывается поддержка Idempotency-Key в create API.
- Ошибки 4xx, включая 402, фиксируются как failed; тот же ID не отправляется вновь.
- Повреждённый журнал не сбрасывается автоматически. Видео-модуль создаётся лениво,
  поэтому отказ его загрузки не должен останавливать остальные маршруты моста.
- Реализация рассчитана на один процесс PC-Bridge на журнал; межпроцессного lock нет.

Опрос и скачивание используют канонический адрес OpenRouter и проверяют provider
ID. Полученные polling_url/unsigned_urls/urls не используются как произвольные
адреса с ключом и не сохраняются. Скачивание допускает HTTPS и до трёх редиректов;
Authorization отправляется только origin https://openrouter.ai. Есть лимит
256 МБ и 120 секунд. Файл сначала пишется в .part; распознаются MP4/WebM по
контейнерному заголовку. Это идентификация контейнера, не полная проверка кодека.
Оборванные временные файлы удаляются. Усечённый кэш скачивается заново без генерации.

## Проверки

13 новых Node-проверок прошли: одно создание при конкурентном повторе и после
перезапуска; параметры модели; 402 и маскировка ключа; unknown после потери ответа;
смерть в submitting; чужой ID; отказ хранения до POST; кэш и усечённый файл;
настоящий локальный HTTP-адаптер; редиректы и предел скачивания. Провайдер и
скачивание инъецированы. Контрольный контейнерный заголовок не является настоящим
сгенерированным или воспроизводимым видео.

Пять JVM-проверок клиента используют настоящие OkHttp и localhost ServerSocket:
один submit → два статуса → download; resume без POST; чужой requestId; 402 и
лимит ожидания; запрет повтора на другой мост при 307. Основная Android-сборка:
`testDebugUnitTest lintDebug assembleDebug` — BUILD SUCCESSFUL за 5m 9s,
305 JVM-тестов без ошибок, lint: 0 errors, 190 warnings.

В этом проходе коммерческий POST /videos не выполнялся: предыдущая живая
медиа-проверка получила 402 от OpenRouter. Поэтому настоящая генерация и
воспроизведение видео пока не подтверждены, даже при зелёных протокольных тестах.

Официальный контракт: [Video Generation](https://openrouter.ai/docs/guides/overview/multimodal/video-generation).
Ссылка отдельной create-reference при повторной проверке вернула 404; использован
действующий официальный guide с submit/poll/content, статусами и discovery.

## Оставшиеся задачи для полного результата

1. Локальный Android checkpoint с исходным мостом/чатом/ключевым источником и
   автоматическое status-only восстановление после смерти процесса. Серверный
   журнал уже работает, но наличие resume-функции не заменяет этот UI-сценарий.
2. Прямой OpenRouter video API на телефоне без PC-Bridge. Этот проход подключает
   путь через мост; отсутствие ПК по-прежнему не обходится одним телефонным ключом.
3. Отдельное управление остановкой наблюдения и отменой у провайдера. Общая кнопка
   остановки текстовой генерации пока не связана с медиа-корутиной; успешная пауза
   не должна выдаваться за подтверждённую отмену платной генерации.
4. Выбор duration/resolution/aspect_ratio в UI, image-to-video и прочие официальные
   параметры. Работающие API-опции моста пока не означают готовый экран настроек.
5. Карточка GeneratedMediaCard всё ещё содержит старые жёсткие подписи MP4/H.264,
   PNG/HD и требует визуальной сверки, выбора локального источника воспроизведения
   и проверки настоящего файла офлайн. Текст сообщения уже не делает этих обещаний.
6. Сквозная проверка настоящего ViewModel: смена чата, остановка, ошибки записи,
   история и восстановление. Unit-тест транспорта не доказывает всё перечисленное.
7. Реальная генерация при доступных кредитах, несколько провайдеров и playback
   MP4/WebM. Ключ не переносился в эмулятор; баланс и настройки не менялись.

Для отката запретить новые generate-video, оставив status/download для уже
существующих задач. Не удалять журнал с неопределёнными/активными запусками и не
повторять их с новыми ID автоматически. Изменения пока локальные, не опубликованы.
