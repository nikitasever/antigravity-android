# Чтение файлов фрагментами на телефоне — 6 ноября 2026

## Найденный дефект

Телефонный read_file загружал обычный текст целиком через readText(), после чего
оставлял только первые 15000 символов. После введения бюджета наблюдений модель
видела ещё меньший префикс. Запросить продолжение было невозможно: offset и limit
не обрабатывались. Повторное чтение снова возвращало начало.

## Исправление

Для phone_action read_file обычный текст читается через Reader с ограниченными
буферами. Параметры: offset по умолчанию 0, limit по умолчанию 3000, допустимо
2–3000. Ответ начинается JSON-заголовком offset/count/nextOffset/hasMore/unit,
затем новой строкой и самим текстом. Единица — UTF-16, как индексы Kotlin String,
не байты и не строки. Метаданные и одна страница помещаются в лимит 4000 символов
одного результата для следующего запроса модели.

Продолжение явно запрашивается по nextOffset. Отрицательные, дробные, null,
boolean, слишком большие значения limit отклоняются до чтения. Смещение за
конец — ошибка; точно в конце допустим пустой результат с hasMore=false.
Суррогатная пара не разрывается на границе страницы, поэтому фактический count
может быть меньше limit. Смещение внутрь пары отклоняется.

Права и разрешение путей остаются прежними. Дочерним исполнителям доступно то
же чтение с прежним запретом записи. Ведущий и ребёнок получают инструкцию о
продолжении и о том, что непереданный остаток ещё не прочитан. Лимиты шагов не
расширяются: большой файл может потребовать отдельного продолжения разговора.

PDF/DOC/DOCX сохраняют существующее извлечение до 15000 символов. Диапазоны для
них отклоняются с понятной ошибкой; ответ без диапазонов сообщает ограничение.
Legacy readFile для естественно-языкового маршрута сохраняет прежний предел
15000, но обычный текст больше не загружает целиком в память.

При большом offset начало проходится последовательно: память ограничена,
стоимость ввода-вывода остаётся пропорциональной смещению. Между запросами файл
может измениться — курсор не фиксирует версию. Бинарные файлы и иные кодировки
не получили нового декодера. Извлечение документов не стало потоковым.

Это реализация собственного телефонного инструмента, а не восстановление
серверного кода Claude/ChatGPT. Визуальные компоненты в этом проходе не менялись.

## Проверка установленного APK

В принадлежащем этой проверке AVD Codex_Reference_UI установлен собранный APK.
В новом чате QA phone file pages выбран режим «Телефон». Вместо платной модели
использован локальный HTTP-сервер на 8798, возвращающий детерминированные
phone_action; настоящий PhoneAgentEngine и PhoneResourceController выполняли
действия Android. Настройки/данные приложения через приватные файлы не подменялись.

Пять модельных запросов, четыре настоящих файловых действия:

1. write_file создал отдельный файл со случайным QA-именем и 6000 символами.
2. read_file без диапазона вернул PAGE_A, nextOffset=3000, hasMore=true.
3. read_file(offset=3000,limit=3000) вернул PAGE_B, nextOffset=6000, hasMore=false.
4. delete_file удалил только этот проверочный файл.
5. Следующий запрос получил успешный результат удаления и вернул итог без действий.

Все четыре серверные проверки — true, stage=5:
`uploads/phone-file-pages-provider-checks.json`. Проверяется не только текст UI:
обе метки и метаданные обнаружены в реально полученных сервером запросах.
